# 01 單元測試：「複式簿記」對帳機制（Go 實作教學）

> 對應指南章節：《企業級 AI 代理人品質驗證與自動化防線架構指南》§2.1 第一重約束

## 核心概念

會計的複式簿記：每筆交易同時記在**借方**與**貸方**，兩邊金額必須相等；不相等就代表有一邊記錯了。

| 會計 | 軟體 | 本專案檔案 |
|---|---|---|
| 借方帳本 | 正式程式碼：**怎麼算** | `pricing.go` |
| 貸方帳本 | 測試程式碼：**應該算出多少** | `pricing_test.go` |
| 試算平衡 | 執行測試 | `go test` |
| 借貸不平 | 紅燈：至少有一本帳錯了 | `FAIL` |

> 🔑 **兩本帳必須「各自獨立記錄」。**
> 貸方若是照抄借方，永遠平衡，對帳毫無意義。
> 帳不平時，由**規格**決定哪一邊錯，而不是看哪一邊比較好改。

## 需求規格

結帳金額計算規則：

1. 小計 = 單價 × 數量
2. 會員打九折
3. **打折後**金額 `>=` 3000 元，再折 300 元

## 專案結構

```
01_單元測試/
├── go.mod
├── pricing.go        # 借方帳本：實作
├── pricing_test.go   # ✅ 貸方帳本：正確答案依規格親手算出、寫死
└── mirror_test.go    # ❌ 反面教材：答案是拿被測的程式自己算的（球員兼裁判）
```

## 動手練習

所有指令都在本目錄下執行。練習 2～4 做完後，記得把 `pricing.go` 和 `pricing_test.go` 還原。

### 練習 1：試算平衡（全綠）

```bash
go test -v ./...
```

所有測試都會 `PASS`，代表兩本帳目前平衡。

### 練習 2：借方記錯 → 真帳抓得到，假帳抓不到

> 📌 輸出很長，`TestFinalPrice_Mirror` 在**最上面**，往上捲才看得到。只想看假帳的話，可以執行 `go test -v -run Mirror ./...`。

**怎麼讀這份輸出：**

- 3 筆 `FAIL` 都是**會員**案例：折扣率錯了，只有會員價會受影響。
- 3 筆 `PASS` 都是**非會員**案例：非會員不打折，所以不受影響。
- 這也說明為什麼測試案例要**涵蓋各種情況**：如果只測非會員，這個錯誤就會漏掉。

**為什麼 `mirror_test.go` 抓不到？** 因為它的正確答案是叫被測的程式自己算的，就像球員兼裁判。程式把九折算成八折，答案也跟著變成八折，兩邊永遠一樣，當然永遠綠燈。

> 💡 檢查方法：問自己「程式寫錯時，我的答案會不會跟著錯？」會的話，這個測試就沒用。

### 練習 3：邊界條件

把 `pricing.go` 中的：

```go
if amount >= threshold {
```

改成 `>`，再執行 `go test ./...`：

```

    --- FAIL: TestFinalPrice/非會員_剛好3000_要折300 (0.00s)
        pricing_test.go:29: FinalPrice(1000, 3, false) = 3000，規格要求 2700（借貸不平）
FAIL
FAIL    doubleentry     0.897s

```

（不加 `-v` 時只會列出失敗的測試，所以這裡看不到綠燈的 `TestFinalPrice_Mirror`。）

只有「剛好 3000」這一筆抓到錯誤。這說明**邊界值**一定要記帳：只測 2000 和 4000 是抓不到這個錯的。`mirror_test.go` 在這個練習裡同樣保持綠燈。

### 練習 4：做假帳（AI 代理人最大的陷阱）

延續練習 2（`memberRate = 80`），**不修實作**，改去修改 `pricing_test.go` 的正確答案，把 `1800` 改成 `1600`、`3300` 改成 `2900`、`2700` 改成 `2400`。

結果全綠，但這個系統現在會對每位會員多打一折，少收原價 10% 的錢。

亮紅燈時，AI 代理人最省力的「改法」就是改測試的正確答案。防範方式：

- **測試的正確答案被修改時，必須由人審查**。正式程式碼可以不逐行看，但測試就是規格，而且又短又好讀，人工審查應該把重點放在這裡。
- 在 CI 中偵測「同一次提交同時修改實作與既有測試斷言」，有的話就標記出來，要求人工確認。

### 練習 5：先記貸方，再記借方

> 這個練習會真的修改程式，做完**不需要**還原。開始前請先確認練習 2～4 的修改都已還原，`go test ./...` 全綠。

新需求：**VIP 會員打八五折**（一般會員仍是九折、非會員原價）。

#### 先想一想：現在的測試裝得下這個需求嗎？

目前測試和程式都用 `isMember bool` 表示身分，只有 `true`（會員）和 `false`（非會員）兩種。**VIP 是第三種身分，`bool` 表示不出來。**

如果直接這樣加：

```go
{"VIP_打八五折", 1000, 2, true, 1700},
```

它的輸入 `(1000, 2, true)` 和既有的 `{"會員_打九折", 1000, 2, true, 1800}` 一模一樣，同一題卻有兩個標準答案，程式不可能兩筆都通過。這時如果把 `memberRate` 改成 85，VIP 那筆會過，但一般會員的 3 筆會全部亮紅燈。這是**舊帳在保護「一般會員九折」這條規格**，複式簿記正在發揮作用。

所以第一步不是加一行測試，而是**先把測試的輸入格式改成能表示三種身分**。

#### 步驟

1. **改測試的輸入格式**：在 `pricing_test.go` 中，把 `isMember bool` 改成 `level MemberLevel`，舊案例的 `true` 改成 `Member`、`false` 改成 `NonMember`。
2. **加入 VIP 案例**，依規格親手算出答案、寫死：

   ```go
   {"VIP_打八五折", 1000, 2, VIP, 1700},
   {"VIP_4000八五折3400再折300", 1000, 4, VIP, 3100},
   {"會員_3500九折3150_會折300", 3500, 1, Member, 2850},
   {"VIP_3500八五折2975_未達門檻", 3500, 1, VIP, 2975}, // 同金額，VIP 反而沒達到滿額門檻
   ```

   最後兩筆特別重要：同樣是 3500 元，一般會員打完九折還有 3150，可以再折 300；VIP 打完八五折只剩 2975，沒到門檻。**規則互相影響**的情況最容易出錯，一定要記一筆。

3. **執行 `go test ./...`，確認紅燈。** 這時會編譯失敗（`undefined: MemberLevel`），因為程式還沒有這個型別。**編譯失敗也算紅燈。**
4. **再改 `pricing.go`**：定義 `MemberLevel`（`NonMember`、`Member`、`VIP`），讓 `FinalPrice` 依等級套用不同折扣率。記得同步修改 `mirror_test.go` 的呼叫方式，否則會編譯不過。
5. **執行 `go test -v ./...`，直到全綠。**

<details>
<summary>參考解答（先自己試，再展開）</summary>

```go
type MemberLevel int

const (
	NonMember MemberLevel = iota
	Member
	VIP
)

func discountRate(level MemberLevel) int {
	switch level {
	case Member:
		return 90
	case VIP:
		return 85
	default:
		return 100
	}
}

func FinalPrice(price, qty int, level MemberLevel) int {
	subtotal := price * qty * discountRate(level) / 100
	return applyThresholdRebate(subtotal)
}
```

</details>

#### 重點

- 先寫測試，答案就只能從規格算出來，不可能照抄程式。指南提到可以接受 AI「先寫函式、再補測試」，但那樣補出來的測試很容易變成 `mirror_test.go` 的樣子。
- **新需求有時會讓舊的測試格式裝不下。** 這時要先調整測試的結構，而不是硬塞一行，或去改舊的答案。

## 學習重點回顧

做完五個練習，你應該學到這些事情：

| 練習 | 你做了什麼 | 學到什麼 |
|---|---|---|
| 1. 試算平衡 | 跑一次測試，看到全綠 | **綠燈代表兩本帳一致**：程式算出來的，和規格要求的一樣。 |
| 2. 借方記錯 | 把九折改成八折 | **答案要跟程式分開算。** 寫死答案的測試抓到錯誤；拿程式自己算答案的測試（球員兼裁判）永遠綠燈。 |
| 3. 邊界條件 | 把 `>=` 改成 `>` | **邊界值一定要測。** 只有「剛好 3000」這一筆抓到錯誤；只測 2000 和 4000 會漏掉。 |
| 4. 做假帳 | 不修程式，改測試的答案 | **綠燈不等於正確。** 改答案讓紅燈變綠燈，就是做假帳。紅燈時要用規格判斷哪邊錯，不是看哪邊好改。 |
| 5. 先記貸方 | 先寫 VIP 測試，再改程式 | **先寫測試，答案就只能從規格來。** 新需求放不進舊格式時，要先調整測試結構，而且舊測試會保護舊規格不被改壞。 |

### 串起來：三個核心觀念

1. **兩本帳要各自獨立記錄。**
   測試的答案必須從規格算出來，不能借用被測的程式。檢查方法：問自己「程式寫錯時，我的答案會不會跟著錯？」
2. **紅燈是好事，它在保護你。**
   練習 2、3、5 的紅燈都是測試在攔截錯誤。真正危險的是不該綠的綠燈（練習 2 的假帳、練習 4 的假帳）。
3. **測試就是規格，要由人來守。**
   正式程式碼可以交給 AI 寫、交給機器量測，但測試的答案代表「需求要的是什麼」。答案被改動時，一定要有人確認。

### 回到 AI 代理人的情境

| 本練習的情況 | 在 AI 代理人開發中的意義 |
|---|---|
| 測試亮紅燈，訊息寫出「得到多少、規格要求多少」 | AI 看得懂錯在哪裡，可以自己退回重改（Backtrack） |
| 假帳永遠綠燈 | AI「先寫程式、再補測試」時最容易寫出這種測試，等於沒有防線 |
| 改答案讓測試變綠 | AI 為了讓測試通過，最省力的做法就是改答案，必須用人工審查或 CI 檢查攔下來 |
| 舊測試抓到一般會員被改壞 | AI 加新功能時常會改壞舊功能，舊測試就是防止這件事的安全網 |

### 自我檢查

能不看文件回答以下問題，就代表你學會了：

- [ ] 為什麼 `mirror_test.go` 永遠是綠燈？
- [ ] 「剛好 3000」這種測試為什麼重要？還有哪些值也算邊界？
- [ ] 測試亮紅燈時，怎麼判斷是程式錯還是測試錯？
- [ ] 如果 AI 提交的變更同時改了程式和測試答案，你應該檢查什麼？
- [ ] 測試覆蓋率很高，能不能代表測試寫得好？為什麼？（提示：試試 `go test -run Mirror -cover ./...`）

## 撰寫真帳的檢查清單

- [ ] 正確答案是**寫死的常數**，依規格親手算出
- [ ] 正確答案的計算**沒有呼叫**任何實作程式碼（函式、常數、helper）
- [ ] 涵蓋**邊界值**（剛好達標、差 1 元）
- [ ] 涵蓋**規則順序**會影響結果的案例（例如「先打折、再判斷滿額」）
- [ ] 失敗訊息說清楚「得到多少、規格要求多少」，讓 AI 代理人能據此回溯（Backtrack）修正

## 延伸

- Go 慣用的 table-driven test 寫法（`pricing_test.go` 中的 `tests` 切片），新增帳目只要加一行。
- 下一步：「第二重約束：CRAP 指標」。覆蓋率高不代表帳記得好。可以用 `go test -run Mirror -cover` 看看，光靠假帳也能拿到不低的覆蓋率。
