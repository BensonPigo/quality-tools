# 考試模式：需求與設計

## 一、需求

| # | 需求 |
|---|---|
| R1 | 大幅減少人工程式碼審查（code review）。人只審第 1 階段（規格書）和第 2 階段（答案卷），程式和測試交給機器檢查 |
| R2 | 三道檢查接進 GitHub 的線上自動檢查（CI），全部通過才能合併回主線 |
| R3 | 檢查在線上自動執行，開發者不用在本機裝工具或下指令 |
| R4 | 規格書和答案卷放在 AI 改不到的地方，修改必須由人核准 |

## 二、預期中的開發流程方式

| 階段 | 產出 | 考試比喻 | 誰做 | 誰把關 |
|---|---|---|---|---|
| 1 | 規格書（Spec）：從使用者收集需求後寫成 | 課本 | 人 | 人工審核 |
| 2 | 答案卷：依照規格書出的題目和標準答案 | 老師出考卷、寫標準答案 | 人 | 人工審核 |
| 3 | 程式：依照規格書寫出來 | 學生作答 | 人/AI | 三道檢查 |
| 4 | 單元測試：依照程式寫的測試，以及把答案卷的題目交給程式作答的那一小段 | 學生自己出的練習題 | 人/AI | 三道檢查 |
| 5 | 閱卷：對答案，跑三道檢查 | 閱卷 | 工具（CI） | — |

第 2、3、4 階段的順序不限，可以同時進行，也可以先寫程式、再補測試。唯一的規定是答案卷依照規格書計算，不參考程式（第 3 階段）的輸出。

人工審核有兩種：業務方確認規則和數字，工程師確認寫法。

## 三、設計

### 1. 單元測試進行方式 - 考試模式

1. 答案卷的每一題都有題目（`input`）和標準答案（`expect`），兩者寫在同一題，一起受保護。
2. 第 4 階段的單元測試只拿得到題目，把題目交給程式算，回傳程式算出的結果，拿不到標準答案。
3. 工具（quality-tools）負責第 5 階段：拿程式算出的結果，對答案卷的標準答案。

題目和答案綁在一起，要換題目就得改答案卷，必須經過人核准。程式那一端看不到答案，沒辦法照著答案湊結果。

答案卷格式範例：

```yaml
# ledger/shipping.yaml
- case: 剛好達免運門檻
  spec: SPEC-3.2
  input:  { subtotal: 1000 }
  expect: { fee: 0 }
```

`spec` 欄位標明這一題對應規格書的哪一條，要不要必填見五、待決定第 2 項。

### 2. 三道檢查

第 4 階段的單元測試是看著程式寫的，證明不了程式算得對，所以「算得對不對」交給答案卷判斷。

**考試模式的程式**（純計算的業務規則）：

| 關卡 | 檢查什麼 | 用哪些測試 |
|---|---|---|
| 第一重：單元測試 | 全部測試都要通過 | 全部 |
| 第二重：複雜度檢查（CRAP） | 程式越複雜、越少被答案卷執行到，分數越高，超過門檻就擋下 | 只用答案卷 |
| 第三重：抓錯檢查（變異測試） | 工具故意把程式改壞，答案卷要抓得到 | 只用答案卷 |

- 第二重只看答案卷執行到程式的哪些部分。寫一堆不檢查結果的測試，也沒辦法灌水。
- 第三重的**抓錯率 ≥ 80%**（工具畫面上叫「效能」）：答案卷有考到的改壞版本裡，至少八成要被抓到。
- 第三重的**考到率**（工具畫面上叫「突變體覆蓋率」）：改壞的地方裡，答案卷有考到的比例。考試模式下門檻必須大於 0，數字等試點決定。考不到的部分，代表程式做了規格書沒寫的事，或是答案卷漏題。
- 如果單元測試沒讓程式真的作答、直接交出寫死的結果，答案卷就完全考不到程式，考到率是 0%，會被第三重擋下。抓錯率只算有考到的部分，完全考不到時擋不住，所以考到率的門檻一定要大於 0。
- 第 4 階段的單元測試在這裡只用在第一重，作用是程式之後被改壞時能馬上發現。

**考試模式以外的程式**（會讀寫資料庫、呼叫外部服務、跟時間有關）：

維持現在的方式，三道檢查都用第 4 階段的單元測試。這只能證明測試抓得到程式的改動，證明不了程式算得對。目前先接受這個限制，等試點跑完，看這類程式佔多少比例，再決定要不要補強，例如由人抽查測試。

### 3. 保護答案卷和規格書

規格書和答案卷放在專案 repo 的 `spec/`、`ledger/`。跟程式放在同一個 repo，規則改的時候，同一個合併申請（PR）就能同時看到程式和答案的修改；目錄名稱固定，下面的保護機制才能用路徑指定。

| 機制 | 作用 | 擋不擋得住 |
|---|---|---|
| Claude Code 設定禁止編輯 `spec/`、`ledger/` 和下一列的設定檔 | AI 一開始就不碰 | 開發者可以自己關掉 |
| 指定審核人（CODEOWNERS） | 指定這些檔案的審核人：`spec/`、`ledger/`，以及 `.quality.json`（門檻設定）、`.github/`（線上檢查設定）、`.gitmodules` 和 `tools/quality`（閱卷工具的版本） | 設在 GitHub 上 |
| 主線保護規則（Branch protection） | 三道檢查全過、審核人核准，才能合併；有新的 commit 就撤銷之前的核准 | 設在 GitHub 上 |

### 4. 執行位置

- **線上自動檢查是最終關卡**，三道檢查都在 GitHub Actions 上跑。
- **本機自動檢查是選配**（Claude Code 的 Stop hook）。本機有裝開發工具（例如 Go、.NET）的人，AI 在本機就會被第一、二重擋下來重修，不用等線上檢查。

## 四、要改的東西

| 位置 | 內容 |
|---|---|
| quality-tools | 先替試點語言加一支對答案的程式，其他語言之後再補；考試模式的程式，第二、三重只用答案卷；考試模式的考到率門檻預設大於 0；`.quality.json` 新增設定，指定哪些目錄套用考試模式 |
| 專案 repo 範本 | 新增 `spec/`、`ledger/`、指定審核人（CODEOWNERS）的範本；Claude Code 設定禁止編輯這兩個目錄；文件寫明主線保護規則怎麼設 |

## 五、待決定

1. **試點專案和語言**：先用一個真實專案、一種語言試跑。
2. **規格書和答案卷要不要逐條對應**：規格書的條目有固定編號（例如 `SPEC-3.2`），答案卷每一題標明對應哪一條。這樣線上檢查可以確認規格書的每一條都至少有一題，審核者也能逐條對照。
