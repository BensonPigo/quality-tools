# 03 變異測試：故意把程式改壞，看測試抓不抓得到（Go 實作教學）

> 對應指南章節：《企業級 AI 代理人品質驗證與自動化防線架構指南》§2.3 第三重約束
> 前一課：`02_CRAP指標`

## 核心概念

覆蓋率只能告訴你「程式有沒有被執行過」，前兩課已經看到它的漏洞：

- 第一課 `mirror_test.go`（標準答案抄學生的作答）：覆蓋率 87.5%
- 第二課練習 4 只呼叫、不檢查答案的測試：覆蓋率 100%，CRAP 全部 PASS，連會員打五折都抓不到

變異測試回答的是另一個問題：**程式被改壞時，測試會不會發現？**

1. 工具自動把程式改壞一個地方，產生一個「突變體」（mutant），例如把 `>=` 改成 `>`。
2. 對每個突變體執行全部測試。
3. 有測試失敗，代表突變體被「消滅」（KILLED），這裡改壞抓得到；全部通過，代表突變體「存活」（LIVED），測試在這裡有漏洞。

你在第一課其實手動做過了：練習 2 把 `90` 改成 `80`、練習 3 把 `>=` 改成 `>`，都是在製造突變體。變異測試工具把這件事自動化，把程式裡每一個 `>=`、`+`、`==`、`&&` 都試著改一遍。

本課使用 Go 的變異測試工具 [gremlins](https://github.com/go-gremlins/gremlins) v0.6.0。指南提到的 PIT 是 Java 的工具，概念相同。

## 執行方式

```bash
go run github.com/go-gremlins/gremlins/cmd/gremlins@v0.6.0 unleash
```

第一次執行會下載 gremlins，整個流程大約 10 秒。要常用的話可以先安裝，之後直接打 `gremlins unleash`：

```bash
go install github.com/go-gremlins/gremlins/cmd/gremlins@v0.6.0
```

### 設定檔 `.gremlins.yaml`

| 設定 | 值 | 原因 |
|---|---|---|
| `unleash.timeout-coefficient` | 30 | gremlins 會依照原本測試跑多久，估出每個突變體的時限。本專案的測試只要幾毫秒，估出來的時限太短，在 Windows 上光重新編譯就超時，結果全部變成 `TIMED OUT`。放寬 30 倍就正常了 |
| `unleash.threshold.efficacy` | 95 | 品質閘門：效能（定義見下方）低於 95% 就判定失敗，結束碼為 10，可以直接放進 CI。**命令列參數 `--threshold-efficacy` 在 v0.6.0 沒有作用，門檻只能寫在設定檔裡** |
| `mutants.invert-logical.enabled` | true | 預設關閉。打開後會把 `&&` 和 `\|\|` 互換 |

### 怎麼讀結果

每個突變體一行，例如：

```
       LIVED CONDITIONALS_BOUNDARY at checkout.go:72:34
```

意思是：把 `checkout.go` 第 72 行第 34 個字元的地方，用 `CONDITIONALS_BOUNDARY` 這種改法改壞之後，測試全部通過，突變體存活了。

**突變體的狀態**

| 狀態 | 意思 |
|---|---|
| `KILLED` | 🟢 有測試失敗，這裡改壞抓得到 |
| `LIVED` | 🔴 測試全部通過，這裡改壞抓不到 |
| `NOT COVERED` | 沒有任何測試執行到這一行，gremlins 不會去測它 |
| `TIMED OUT` | 測試跑太久被中止（通常是改壞後變成無窮迴圈，或時限設太短） |
| `NOT VIABLE` | 改完之後編譯不過 |

**改法（mutator）**

| 改法 | 做什麼 | 檢查什麼 |
|---|---|---|
| `CONDITIONALS_BOUNDARY` | `>=` ↔ `>`、`<=` ↔ `<` | 邊界值有沒有測 |
| `CONDITIONALS_NEGATION` | `==` ↔ `!=`、`>=` ↔ `<` 等，把條件反過來 | 條件成立和不成立有沒有都測 |
| `ARITHMETIC_BASE` | `+` ↔ `-`、`*` ↔ `/` 等 | 計算結果有沒有被檢查 |
| `INVERT_NEGATIVES` | 把負號拿掉 | 計算結果有沒有被檢查 |
| `INCREMENT_DECREMENT` | `++` ↔ `--` | 迴圈或計數有沒有被檢查 |
| `INVERT_LOGICAL` | `&&` ↔ `\|\|` | 複合條件的每一部分有沒有分別測 |

gremlins 不會修改常數的值，所以第二課練習 4「把 `90` 改成 `50`」這種改法不在它的清單裡。不過 `return 90` 這一行仍然被其他改法間接檢查到：例如把 `line * discountRate(level) / 100` 的 `*` 改成 `/`，只要測試有檢查會員價，就抓得到。

**最後的統計**

| 數字 | 計算方式 | 回答什麼問題 |
|---|---|---|
| Test efficacy（效能） | KILLED ÷（KILLED + LIVED） | 測試跑到的地方，改壞了抓得到幾成？ |
| Mutator coverage（突變覆蓋率） | （KILLED + LIVED）÷ 全部突變體 | 有幾成的突變體，至少有測試執行到？ |

### 練習 2：換上真測試

把 `checkout_test.go` 換成第二課練習 2 的真測試：

<details>
<summary>checkout_test.go 完整內容（展開後複製）</summary>

```go
package checkout

import "testing"

// 第二課練習 2 的真測試：每個 want（正確答案）都依需求規格親手算出、寫死。
func TestCheckout(t *testing.T) {
	tests := []struct {
		name   string
		items  []Item
		level  MemberLevel
		coupon string
		want   int
	}{
		{"空購物車", nil, NonMember, "", 0},
		{"非會員_500元_加運費100", []Item{{500, 1, false}}, NonMember, "", 600},
		{"數量0略過_只算300_加運費100", []Item{{500, 0, false}, {300, 1, false}}, NonMember, "", 400},
		{"會員_4000九折3600_滿額折300_免運", []Item{{2000, 2, false}}, Member, "", 3300},
		{"VIP_500八五折425_VIP免運", []Item{{500, 1, false}}, VIP, "", 425},
		{"會員_特價品不打折", []Item{{1000, 1, true}}, Member, "", 1000},
		{"SAVE100_1200折100", []Item{{1200, 1, false}}, NonMember, "SAVE100", 1100},
		{"SAVE100_1050折完950_要運費", []Item{{1050, 1, false}}, NonMember, "SAVE100", 1050},
		{"HALFSHIP_運費50", []Item{{500, 1, false}}, NonMember, "HALFSHIP", 550},
		{"FREESHIP_免運", []Item{{500, 1, false}}, NonMember, "FREESHIP", 500},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got := Checkout(tt.items, tt.level, tt.coupon)
			if got != tt.want {
				t.Errorf("Checkout() = %d，規格要求 %d（答錯了）", got, tt.want)
			}
		})
	}
}
```

</details>

先執行 `go test ./...` 確認全綠，再執行 gremlins：

```
       LIVED CONDITIONALS_BOUNDARY at checkout.go:41:13
       LIVED CONDITIONALS_BOUNDARY at checkout.go:72:34
       LIVED CONDITIONALS_BOUNDARY at checkout.go:80:11
Killed: 21, Lived: 3, Not covered: 0
Test efficacy: 87.50%
ERROR: below efficacy-threshold
```

（只列出重點行，21 行 `KILLED` 和進度訊息省略。）

24 個消滅了 21 個，進步很多，但還沒過 95% 的門檻。**先別急著看答案**，打開 `checkout.go`，找到這三行，想想看：

- 這三個突變體分別把程式改成什麼樣子？
- 改完之後，哪一種購物車會算出不同的金額？
- 為什麼現有的 10 筆測試都沒抓到？

<details>
<summary>分析</summary>

三個都是 `CONDITIONALS_BOUNDARY`，也就是 `>=` 和 `>`、`<=` 和 `<` 互換：

| 位置 | 原本 | 改成 | 為什麼沒被抓到 |
|---|---|---|---|
| 第 41 行 | `it.Qty <= 0` | `it.Qty < 0` | 練習 4 再談 |
| 第 72 行 | `total >= 1000`（SAVE100 門檻） | `total > 1000` | 沒有「剛好 1000 元用 SAVE100」的測試 |
| 第 80 行 | `total >= 3000`（滿額門檻） | `total > 3000` | 沒有「剛好 3000 元」的測試 |

第一課練習 3 學過：邊界值一定要測。這裡變異測試自動找出了兩個漏測的邊界。

</details>

### 練習 3：補邊界測試

**先補滿額門檻。** 在測試表格加一筆「剛好 3000 元」的案例，正確答案依規格親手算。

**再補 SAVE100 門檻。** 最直覺的寫法是「非會員買一件 1000 元的商品，用 SAVE100」：

```go
{"SAVE100_剛好1000_直覺寫法", []Item{{1000, 1, false}}, NonMember, "SAVE100", 1000},
```

依規格算：1000 元滿門檻，折 100 剩 900；900 未滿 1000，加運費 100；結果 **1000**。

加進去之後執行 gremlins，你會發現第 72 行的突變體**還是存活**。為什麼？

<details>
<summary>原因</summary>

把突變體的算法也走一次：`>` 的版本認為 1000 元沒有超過門檻，所以不折；1000 元不用運費；結果也是 **1000**。

原本的程式和突變體算出同樣的金額，只是過程不同：一個「折 100、再收 100 運費」，一個「不折、不收運費」。折掉的 100 元剛好被運費抵消了。

**邊界測試的輸入值選對了還不夠，還要確認結果不會被其他規則抵消。** 要避開運費這條規則，可以讓顧客本來就免運，例如用 VIP，而且買特價品才不會被八五折影響金額：

```go
{"VIP_特價1000_SAVE100剛好門檻_折100", []Item{{1000, 1, true}}, VIP, "SAVE100", 900},
```

原本的程式：1000 → 折 100 → 900，VIP 免運 → **900**；突變體：1000 不折，VIP 免運 → **1000**。兩者不同，突變體就被消滅了。

滿額門檻的參考寫法：

```go
{"非會員_剛好3000_要折300", []Item{{1000, 3, false}}, NonMember, "", 2700},
```

</details>

刪掉直覺寫法那一筆，換成能消滅突變體的版本，加上剛好 3000 的案例，再執行一次（只列出重點行）：

```
       LIVED CONDITIONALS_BOUNDARY at checkout.go:41:13
Killed: 23, Lived: 1, Not covered: 0
Test efficacy: 95.83%
```

效能 95.83%，通過門檻，沒有出現 `ERROR`。

### 練習 4：殺不死的突變體

最後剩下第 41 行：

```go
if it.Qty <= 0 {   // 突變體改成 it.Qty < 0
	continue
}
```

試著寫一筆測試消滅它。你會發現做不到，原因是：

- 原本的程式：數量 0 的商品被略過。
- 突變體：數量 0 的商品不會被略過，但它的金額是「單價 × 0 = 0」，加進總額也不影響結果。

不管購物車放什麼，兩者算出來的金額永遠一樣。這種突變體叫做**等價突變體**（equivalent mutant）：改了程式，行為卻完全沒變，所以任何測試都殺不死它。

遇到存活的突變體，要先判斷它屬於哪一種：

| 判斷 | 處理方式 |
|---|---|
| 測試漏了（練習 2、3 的邊界） | 依規格補測試 |
| 等價突變體（練習 4） | 接受它存活，在門檻上預留空間 |

本專案共 24 個突變體，其中 1 個是等價突變體，效能最高只能到 23 ÷ 24 = 95.83%。門檻設 95% 就是留了這一個的空間。門檻要依專案實際情況設定，不能一律要求 100%：等價突變體多的程式，設 100% 永遠過不了。

不要為了消滅等價突變體去改程式，例如把 `<= 0` 改成 `< 0`。這樣做會讓數量 0 的商品進入計算，程式和規格的對應就變得不直覺了；而且 `< 0` 本身又會產生一個新的等價突變體（改成 `<= 0`），問題根本沒解決。

## 學習重點回顧

| 練習 | 你做了什麼 | 學到什麼 |
|---|---|---|
| 1. 假測試 | 對只呼叫不檢查的測試跑 gremlins | **覆蓋率 100%、CRAP 全過的測試，效能可能是 0%。** 變異測試能抓出前兩重約束抓不到的假測試。 |
| 2. 真測試 | 換上第二課的 10 筆真測試 | **存活的突變體會指出測試漏了哪裡。** 三個存活突變體中，有兩個是缺邊界測試。 |
| 3. 補邊界 | 補「剛好 1000」「剛好 3000」的測試 | **邊界測試的結果可能被其他規則抵消。** 直覺寫法殺不死突變體，要選讓兩種算法結果不同的輸入。 |
| 4. 等價突變體 | 嘗試消滅 `Qty <= 0` 的突變體 | **有些突變體不可能被消滅。** 存活的突變體要由人判斷是測試漏了還是等價，門檻也要預留空間。 |

### 三重約束串起來

| 約束 | 檢查什麼 | 會被什麼騙過 | 由誰補上 |
|---|---|---|---|
| 第一重：單元測試 | 答案對不對 | 程式寫得再亂都不管 | 第二重 |
| 第二重：CRAP | 結構風險（複雜度 × 覆蓋率） | 只呼叫、不檢查答案的假測試 | 第三重 |
| 第三重：變異測試 | 程式被改壞時，測試抓不抓得到 | 依程式輸出寫答案的測試（見下方） | 人的審查 |

### 回到 AI 代理人的情境

指南描述的流程是：AI 代理人執行變異測試，讀取存活突變體的報告，自動補測試，直到全部消滅。實際操作有三件事要注意：

**1. AI 補測試時，正確答案仍然要從需求規格來。**
AI 最省事的做法是：把突變體位置的輸入丟進程式，拿程式目前的輸出當正確答案。這樣確實能消滅突變體，但等於回到第一課抄學生作答的答案卷。程式如果本來就有 bug，這個 bug 會被測試鎖住，以後反而沒人發現。

**2. AI 要能分辨等價突變體。**
不然它會在練習 4 這種地方無限重試。給 AI 的指令要包含：「判斷為等價突變體時，停止並回報理由，交給人確認」。

**3. 練習 3 的陷阱 AI 也會掉進去。**
AI 補了一筆看起來正確的邊界測試，突變體卻沒死，它可能會改成更奇怪的輸入硬湊。重新跑 gremlins 確認突變體真的被消滅，是 AI 每補一筆測試都要做的檢查。

這套流程在本專案跑一次大約 10 秒；指南提到 AI 代理人執行 PIT 大約要 30 分鐘。突變體數量和測試時間成正比，專案越大，越需要只針對變更的部分跑。gremlins 的 `--diff` 參數就是用來只測某個分支或 commit 改過的程式。
