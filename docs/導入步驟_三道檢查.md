# 三道檢查導入步驟

把《企業級 AI 代理人品質驗證與自動化防線架構指南》說的三道檢查（單元測試、CRAP、抓錯檢查），導入一個已經開發到一半的系統。

## 用詞對照

這份文件用白話的說法，工具畫面和網路文章用的是右邊的名詞。

| 本文說法 | 意思 | 工具和文章裡的名詞 |
|---|---|---|
| 抓錯檢查 | 工具故意把程式改壞，看測試抓不抓得到 | 變異測試（Mutation Testing） |
| 改壞的版本 | 工具改壞程式的每一種改法，例如把 `>=` 改成 `>` | 突變體（Mutant） |
| 抓到 / 沒抓到 | 改壞之後，測試會失敗就是抓到，測試照樣通過就是沒抓到 | 殺死（Killed）/ 存活（Survived） |
| 抓錯率 | 有測到的改壞版本裡，抓到幾成 | 效能（Mutation Score、Efficacy） |
| 測到率 | 全部改壞版本裡，有幾成被測試跑到 | 突變體覆蓋率（Mutant Coverage） |
| 改了也沒差的版本 | 怎麼改，程式的結果都一樣，所以不可能抓到 | 等價突變體（Equivalent Mutant） |
| CI | 推上 GitHub 或 GitLab 後，自動在線上跑的檢查 | 持續整合（Continuous Integration） |

## 一、總覽

| 步驟 | 做什麼 | 怎麼做 | 為什麼 |
|---|---|---|---|
| 0. 先量現況 | 在現有程式上跑一次三道檢查，存成報告 | 依語言挑工具（見四、五節），結果整理成表格，commit 進 repo | 這份報告就是技術債清單。很多函式不及格是正常的 |
| 1. 只管這次改到的 | 這次改到的函式要及格，沒改到的先不管 | 用 `git diff main...HEAD` 找出改到哪幾行，對照每個函式從第幾行到第幾行，只檢查有改到的函式 | 開發到一半的系統有很多舊程式不及格。要求全部及格的話，第一天就卡死 |
| 2. 上單元測試這關 | 每個 PR 都跑全部測試，沒過就不能合併 | 在 GitHub Actions 或 GitLab CI 加一個步驟跑測試（例如 `dotnet test`），送 PR 時自動執行 | 最簡單，效果最直接 |
| 3. 上 CRAP | 改到的函式分數超過 12 就擋下 | 見四節 | 逼 AI 補測試，或把太複雜的函式拆小 |
| 4. 上抓錯檢查 | 只在 CI 跑，只算改到的那幾行 | 見五節 | 確認程式被改壞時，測試真的抓得到 |
| 5. AI 自己先檢查 | AI 說「做完了」之前，自動跑單元測試和 CRAP，沒過就把錯誤丟回去重修 | Claude Code 用 Stop hook（AI 要結束時自動執行的腳本）跑這兩關，沒過就回報錯誤，AI 會接著修。其他 AI 工具找類似「結束前執行」的功能 | 大部分問題在送到 CI 之前就修掉了 |
| 6. 把規則鎖起來 | AI 不能改門檻和 CI 設定，要改得經過人核准。main 分支要三關全過、加上人核准，才能合併 | 三個地方一起設：AI 工具的權限設定，禁止編輯這些檔案；CODEOWNERS 指定這些檔案由誰審核；main 分支保護規則，要求檢查全過、至少一人核准。AI 用的帳號不給合併權限 | 不鎖的話，AI 卡關時可能直接把門檻調低 |
| 7. 人改成看測試 | 人不用一行一行看程式，但要看測試的正確答案對不對 | 審 PR 時先看測試檔改了什麼：正確答案是不是照需求寫的、測試有沒有被刪掉或改鬆。這條規則也寫進 AI 的指示檔（例如 CLAUDE.md） | 三道檢查只能證明測試抓得到程式被改動。AI 如果把正確答案改成跟著程式算，三關照樣全過 |

一次上一關，先跑一兩週，看會不會常常擋錯，再上下一關。全部一次上的話，出問題時分不出是哪一關設錯。

## 二、技術債怎麼處理

第 0 步量出來的技術債，主要靠第 1 步的規則慢慢消化：改到哪裡，清到哪裡。有人改到一個舊函式，就得順手補測試或拆小。常改的程式會最先變乾淨，很少動的程式就算留著，通常也不會出事。

不停下來一次全部清完，原因有三個：

- 舊程式大多沒有測試，直接大改很容易改壞。
- 清技術債的這段時間，新功能都得停下來。
- 有些程式之後根本不會再動，花時間清它划不來。

例外：同時符合下面兩點的函式，要主動排進開發排程先處理。

1. CRAP 分數很高，或被標成「要拆函式」
2. 最近常被修改（用 `git log` 看改過幾次）

這種函式不先處理的話，下次有人要改它，本來只是一個小改動，卻被迫一起補測試、拆函式，PR 會變得很大，也會讓人想偷偷繞過檢查。

每一季重新量一次，跟第 0 步的報告比，看不及格的函式有沒有變少。數字一直沒降，代表大家都在避開舊程式，這時候才需要另外排時間專門清。

## 三、第一關：單元測試

每個 repo 自己寫單元測試，CI 在每個 PR 跑一次。

指南拿會計的「複式簿記」來比喻單元測試：

| 會計 | 軟體 |
|---|---|
| 帳本一：錢從哪裡來 | 程式：怎麼算 |
| 帳本二：錢花到哪裡去 | 測試：應該算出多少 |
| 兩本對不起來，代表有一邊記錯 | 測試失敗，代表程式或測試有一邊錯 |

這個比喻要成立，兩本帳必須分開記：**測試的正確答案要照需求直接寫出來，不能叫程式算**。例如需求是「滿 1000 元免運，未滿收 60 元」：

```go
// 對：正確答案照需求直接寫
func TestShipping(t *testing.T) {
    if got := ShippingFee(999); got != 60 { t.Errorf("999 元應收 60，得到 %d", got) }
    if got := ShippingFee(1000); got != 0 { t.Errorf("1000 元應免運，得到 %d", got) }
}

// 錯：正確答案叫程式自己算
func TestShipping(t *testing.T) {
    expected := ShippingFee(1000)  // 程式算錯，答案就跟著錯
    if got := ShippingFee(1000); got != expected { ... }
}
```

錯的寫法等於兩本帳抄同一份，永遠對得上，也就失去對帳的意義。

AI 同時寫程式和測試時，可能會把程式算出來的結果直接抄進測試。所以要做兩件事：

1. 在 AI 的指示檔寫清楚：「測試的正確答案要照需求直接寫，不准呼叫正式程式算出來。」
2. 審 PR 時，人要確認測試的正確答案跟需求一致（總覽第 7 步）。

## 四、第二關：CRAP

CRAP 是一個分數：函式越複雜、被測試跑到的越少，分數越高，超過門檻就擋下。它要用到每個函式的兩個數字：圈複雜度（函式裡有幾條路可以走，`if`、`switch`、迴圈越多，數字越大）和覆蓋率（函式裡有幾成程式碼被測試跑到）。大部分語言沒有現成工具能直接算出 CRAP，所以要用兩個工具各量一個數字，再寫一支程式合起來算。

| 步驟 | 做什麼 | 怎麼做 |
|---|---|---|
| 1. 量圈複雜度 | 每個函式有幾條路可以走 | Go 用 gocyclo、Python 用 radon、JS/TS 用 ESLint 的 `complexity` 規則、C# 用 Roslyn 分析器 |
| 2. 量覆蓋率 | 每個函式有幾成程式碼被測試跑到 | 跑測試時順便產生覆蓋率報告：Go 用 `go test -coverprofile`、C# 用 coverlet、Python 用 coverage.py、JS 用 Vitest 或 Jest 加 `--coverage` |
| 3. 合起來算分數 | 用函式名稱和行號，把兩份報告對起來，套公式 `C² × (1−p)³ + C`（C 是圈複雜度，p 是覆蓋率） | 寫一支小程式讀這兩份報告，算出每個函式的分數 |
| 4. 只看改到的函式 | 舊函式先不管 | 用 `git diff main...HEAD` 找出改到的行，只留下有改到的函式 |
| 5. 判斷過不過 | 分數超過門檻就算失敗 | 門檻寫在設定檔（例如 12）。超過時讓程式回報失敗，CI 就會變紅 |
| 6. 告訴 AI 怎麼修 | 每個超標的函式，標出該怎麼改 | 見下方 |
| 7. 接進 CI | 排在單元測試後面 | 在 CI 設定檔加一個步驟，執行這支程式 |

**怎麼判斷該拆函式還是補測試**：測試把函式全部跑到時，CRAP 就等於圈複雜度。所以：

- 圈複雜度超過門檻：測試補再多也過不了，只能拆函式。
- 圈複雜度沒超過門檻：補測試就能過，而且算得出覆蓋率要到多少。例如圈複雜度 5、門檻 12，覆蓋率要到大約 35%。

報告直接寫「要拆函式」或「覆蓋率要到 35%」，AI 就知道該往哪個方向改。

**有現成工具的語言**：C# 用 ReportGenerator 讀 coverlet 的報告，就會列出每個函式的 CRAP 分數（在 Risk Hotspots 頁）；PHP 的 PHPUnit 覆蓋率報告直接附 CRAP 分數；Java 的 crap4j 已經沒人維護，通常還是拿 JaCoCo 的報告自己算。就算有現成工具，「只看改到的函式」和「超標就讓 CI 失敗」這兩段，大多還是要自己補一小段腳本。

## 五、第三關：抓錯檢查

工具故意把程式改壞（例如把 `>=` 改成 `>`），再跑一次測試，看測試抓不抓得到。

| 步驟 | 做什麼 | 怎麼做 |
|---|---|---|
| 1. 挑工具 | 每種語言選一個 | Java 用 PIT、C# 用 Stryker.NET、JS/TS 用 StrykerJS、Go 用 gremlins、Python 用 cosmic-ray 或 mutmut |
| 2. 只改壞這次改到的行 | 整個專案跑一次可能要好幾個小時 | 用 `git diff main...HEAD` 找出改到的行交給工具。Stryker 可以指定檔案和行號；做不到的工具就整個跑完，再把其他行的結果過濾掉 |
| 3. 算兩個比例 | 每個改壞的版本，結果會是這幾種之一：抓到、沒抓到、逾時、測試根本沒跑到 | **抓錯率** = 抓到 ÷（抓到 + 沒抓到），逾時的算抓到。**測到率** = 有被測試跑到的 ÷ 全部 |
| 4. 判斷過不過 | 兩個比例都要達到門檻 | 抓錯率的門檻參考第 0 步的現況，例如 80%。測到率也要設門檻，原因見下方 |
| 5. 告訴 AI 怎麼修 | 列出每個沒抓到的改壞版本 | 寫出檔案、行號、改了什麼，例如「第 42 行的 `>=` 改成 `>`，測試還是通過」。AI 一看就知道邊界值沒測到 |
| 6. 處理不可能抓到的 | 有些改法，程式結果完全一樣（改了也沒差的版本） | 規定 AI 不准為了它亂寫測試，要列出位置和理由，交給人判斷。人確認後，在工具的設定裡把它排除 |
| 7. 接進 CI | 排在 CRAP 後面，只在送 PR 時跑 | 太慢了，不放進 AI 結束前的自動檢查。改壞的版本很多時，可以開多個同時跑，或設定逾時秒數 |

**測到率一定要設門檻**：抓錯率只算有被測試跑到的部分。一段完全沒寫測試的新程式，改壞的版本全都「沒被測試跑到」，根本不算進抓錯率，抓錯率當然不會下降。CRAP 也不一定擋得住：圈複雜度 1 的函式，沒有測試也只有 2 分。所以只設抓錯率的話，新程式完全不寫測試，三關反而都會過。設一個測到率門檻（例如 50%），才擋得住這種情況。

**抓錯率不要設 100%**：改了也沒差的版本不可能抓到，設 100% 會逼 AI 寫出奇怪的測試，或想辦法繞過檢查。

**CI 會變慢**：只跑改到的行的話，一般 PR 幾分鐘就跑完；改到大檔案或核心模組時，可能要十幾二十分鐘，要先跟團隊講好。

## 六、哪些工作做成共用工具

量數字的工具（gocyclo、coverlet、Stryker 這些）都是現成的，不用自己開發。要做成共用工具的，是把這些工具串起來的那支程式，第二、三關共用同一支。

**共用工具負責：**

| 工作 | 原因 |
|---|---|
| 呼叫各語言的量測工具，轉成同一種格式 | 每個工具的報告格式都不一樣，轉換寫一次就好 |
| 用 git diff 找出改到的函式和行 | 這段最容易寫錯（例如只改註解算不算改到），每個 repo 各寫一份，就會各錯各的 |
| 算 CRAP 分數、抓錯率、測到率 | 算法和歸類方式（例如逾時算不算抓到）全公司統一，分數才能互相比較 |
| 判斷有沒有過門檻、標出該怎麼改 | 大家用同一套判斷 |
| 產生報告（超標的函式、沒抓到的改壞版本） | 格式統一，AI 只要看懂一種格式 |
| 固定量測工具的版本 | 抓錯檢查的工具改版時，改壞程式的方式可能會變，分數也會跟著變 |
| 提供預設的工具設定 | 逾時秒數、同時跑幾個、預設排除哪些改法 |

**各 repo 自己負責：**

| 工作 | 原因 |
|---|---|
| 寫單元測試 | 覆蓋率要靠測試量，改壞的版本要靠測試抓 |
| 設定檔：語言、門檻、不檢查的目錄 | 每個 repo 現況不同，參考自己第 0 步的報告決定門檻 |
| 判斷哪些是改了也沒差的版本，記錄要排除的清單 | 要看懂業務邏輯才判斷得出來。清單放在各 repo，也要鎖起來，改了要人核准 |
| 安裝語言專用的套件 | 例如 StrykerJS 要寫進 `package.json`，版本才能跟專案的測試框架搭配 |
| 在 CI 呼叫三個指令 | 跑測試、CRAP、抓錯檢查 |

做成共用工具之後，修一個 bug 或調整一次算法，各 repo 升級版本就跟著修好。判斷的程式不放在各 repo 裡，AI 也改不到。

**發給各 repo 的方式：**

| 方式 | 說明 |
|---|---|
| git submodule | 各 repo 掛一個目錄，指向工具的某個版本，要升級時改版本號 |
| 套件（pip、npm、NuGet） | 各 repo 當成開發用套件安裝 |
| 共用的 CI 設定 | 例如 GitHub 的 reusable workflow，各 repo 的 CI 只要寫一行引用 |

不管用哪種方式，都要固定版本。工具一更新、判斷變嚴格，所有 repo 會同時變紅，所以讓各 repo 自己決定什麼時候升級。
